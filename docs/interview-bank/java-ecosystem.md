## Сборка и зависимости: Maven и Gradle { #build }

<a id="java-161"></a>

**161. Что входит в жизненный цикл Maven?** · junior
**Ориентир:** Maven выполняет фазы стандартных lifecycle: `clean`, `default` и `site`; вызов фазы запускает и все предыдущие фазы этого lifecycle. Конкретную работу делают goals плагинов, привязанные к фазам.

<a id="java-162"></a>

**162. Чем dependency scope `compile`, `runtime`, `provided` и `test` отличается в Maven?** · junior
**Ориентир:** Scope определяет, где зависимость доступна и попадёт ли она в runtime classpath и транзитивные зависимости. Например, `provided` ожидается от среды запуска, а `test` используется только при компиляции и запуске тестов.

<a id="java-163"></a>

**163. Как Maven разрешает конфликт транзитивных версий?** · middle
**Ориентир:** Обычно побеждает ближайшее объявление в дереве зависимостей, а при одинаковой глубине — первое объявленное. Версии лучше фиксировать централизованно через `dependencyManagement` и проверять командой `dependency:tree`.

<a id="java-164"></a>

**164. Для чего нужны BOM и `dependencyManagement`?** · middle
**Ориентир:** BOM согласует совместимые версии набора библиотек, а `dependencyManagement` задаёт версии и параметры без автоматического добавления зависимостей в модуль. Это уменьшает дрейф версий в multi-module проекте.

<a id="java-165"></a>

**165. Чем Maven-плагин отличается от обычной зависимости?** · junior/middle
**Ориентир:** Зависимость попадает в classpath приложения или тестов, а плагин исполняет build goals внутри Maven. Версии плагинов также нужно фиксировать для воспроизводимости сборки.

<a id="java-166"></a>

**166. Что такое Gradle task и как формируется task graph?** · junior/middle
**Ориентир:** Task — единица работы со входами, выходами и зависимостями от других tasks. Gradle сначала конфигурирует граф запрошенных задач, затем исполняет его с учётом порядка и актуальности результатов.

<a id="java-167"></a>

**167. Чем конфигурации Gradle `implementation`, `api`, `compileOnly` и `runtimeOnly` отличаются?** · middle
**Ориентир:** `implementation` скрывает зависимость от compile classpath потребителя, а `api` экспортирует её через публичный API библиотеки. `compileOnly` нужна лишь при компиляции, `runtimeOnly` — только во время исполнения.

<a id="java-168"></a>

**168. Зачем использовать Maven Wrapper или Gradle Wrapper?** · junior
**Ориентир:** Wrapper запускает зафиксированную проектом версию build tool без предварительной системной установки. Это сближает локальную сборку и CI, но версию JDK и внешние сервисы всё равно нужно согласовать отдельно.

<a id="java-169"></a>

**169. Что делает сборку воспроизводимой?** · middle/senior
**Ориентир:** Фиксированные версии JDK, wrapper, плагинов и зависимостей, lock/checksum-проверки и отсутствие изменяемых артефактов вроде `SNAPSHOT` снижают расхождения. Сборка также не должна зависеть от локальных файлов, времени или неявного состояния машины.

<a id="java-170"></a>

**170. Как ускорять Maven- или Gradle-сборку без потери надёжности?** · senior
**Ориентир:** Сначала измеряют время конфигурации, компиляции и тестов, затем применяют build cache, incremental build, параллельность и разделение тестов. Кэш в CI должен иметь корректные ключи и не подменять проверку чистой сборкой.

## Тестирование: JUnit, Mockito и Testcontainers { #testing }

<a id="java-171"></a>

**171. Чем unit-, integration- и end-to-end-тесты отличаются?** · junior
**Ориентир:** Unit-тест изолированно проверяет небольшую единицу логики, integration — взаимодействие компонентов или инфраструктуры, end-to-end — пользовательский сценарий через всю систему. Граница определяется реальными зависимостями теста, а не именем каталога.

<a id="java-172"></a>

**172. Каков жизненный цикл теста в JUnit Jupiter?** · junior
**Ориентир:** `@BeforeEach` и `@AfterEach` окружают каждый тест, `@BeforeAll` и `@AfterAll` — весь класс. По умолчанию JUnit создаёт новый экземпляр тестового класса для каждого метода, если не выбран `PER_CLASS`.

<a id="java-173"></a>

**173. Когда применять parameterized tests?** · junior/middle
**Ориентир:** Когда один контракт нужно проверить на наборе входов и ожидаемых результатов без копирования тестового кода. Источники аргументов должны оставлять каждый кейс понятным по имени и причине существования.

<a id="java-174"></a>

**174. Для чего нужны nested tests и display names?** · junior
**Ориентир:** `@Nested` группирует сценарии по состоянию или поведению, а `@DisplayName` делает отчёт читаемым. Структура полезна, пока не скрывает чрезмерно сложный setup.

<a id="java-175"></a>

**175. Что следует проверять через `assertThrows`?** · junior
**Ориентир:** Не только тип исключения, но при необходимости сообщение, cause или доменные поля. Проверяемый вызов должен быть минимальным, чтобы тест не прошёл из-за исключения в подготовительном коде.

<a id="java-176"></a>

**176. Чем mock, stub и spy отличаются?** · junior/middle
**Ориентир:** Stub отдаёт заранее заданные ответы, mock дополнительно проверяет взаимодействия, spy оборачивает реальный объект и частично переопределяет поведение. Spy хрупок при побочных эффектах, поэтому его используют осознанно.

<a id="java-177"></a>

**177. Когда Mockito `verify` полезен, а когда делает тест хрупким?** · middle
**Ориентир:** Проверка взаимодействия уместна для важного внешнего эффекта или протокола, который нельзя наблюдать через результат. Проверять каждый внутренний вызов опасно: рефакторинг реализации ломает тест при неизменном поведении.

<a id="java-178"></a>

**178. Чем `when(...).thenReturn(...)` отличается от `doReturn(...).when(...)`?** · middle
**Ориентир:** Обычный стиль вызывает метод внутри `when`, что проблемно для spy или некоторых void/final сценариев. Семейство `doReturn`, `doThrow` и `doAnswer` задаёт поведение без такого вызова; для чистых mocks обычно читаемее `when`.

<a id="java-179"></a>

**179. Почему не стоит мокать value objects и собственную бизнес-логику?** · middle
**Ориентир:** Моки полезнее на границах с I/O и нестабильными зависимостями. Мокирование простых объектов и соседних частей домена связывает тест с реализацией и может подтвердить выдуманное поведение вместо реального контракта.

<a id="java-180"></a>

**180. Что даёт Testcontainers?** · junior/middle
**Ориентир:** Он запускает одноразовые контейнеры реальных баз, брокеров и других сервисов для интеграционных тестов. Это повышает реалистичность, но требует контролировать startup time, очистку данных и доступность container runtime.

<a id="java-181"></a>

**181. Как управлять жизненным циклом контейнера в тестах?** · middle
**Ориентир:** Контейнер можно поднимать на класс или переиспользовать в пределах процесса, сохраняя изоляцию данных между тестами. Статический контейнер ускоряет suite, но тесты не должны зависеть от порядка или оставленного состояния.

<a id="java-182"></a>

**182. Как тестировать миграции БД?** · middle/senior
**Ориентир:** Поднять поддерживаемую версию реальной СУБД, применить миграции с нуля и отдельно проверить обновление с репрезентативной предыдущей схемы. In-memory БД не всегда воспроизводит диалект, блокировки и ограничения production-СУБД.

## Spring: Core, Boot, MVC, Data, транзакции и Security { #spring }

<a id="java-183"></a>

**183. Что такое IoC и dependency injection в Spring?** · junior
**Ориентир:** Контейнер создаёт объекты, связывает зависимости и управляет их жизненным циклом. Constructor injection делает обязательные зависимости явными и облегчает тестирование без контейнера.

<a id="java-184"></a>

**184. Чем `BeanFactory` отличается от `ApplicationContext`?** · middle
**Ориентир:** `BeanFactory` задаёт базовый контейнер, а `ApplicationContext` добавляет события, сообщения, environment, resource loading и интеграцию с инфраструктурой Spring. В приложениях обычно работают с `ApplicationContext`.

<a id="java-185"></a>

**185. Каков жизненный цикл Spring bean?** · middle
**Ориентир:** После создания и внедрения зависимостей выполняются aware callbacks, bean post-processors и init callbacks; при закрытии контекста — destroy callbacks. Прокси может означать, что вызывающий код работает не с исходным экземпляром.

<a id="java-186"></a>

**186. Чем singleton scope Spring отличается от singleton-паттерна?** · junior/middle
**Ориентир:** Spring singleton означает один bean на `ApplicationContext` и имя bean, а не один объект на JVM. Он не становится потокобезопасным автоматически, поэтому изменяемое request-specific состояние в нём опасно.

<a id="java-187"></a>

**187. Как Spring разрешает несколько beans одного типа?** · junior
**Ориентир:** Можно уточнить выбор через `@Qualifier`, имя bean или назначить `@Primary`. Если однозначного кандидата нет, контейнер обычно завершит создание контекста ошибкой.

<a id="java-188"></a>

**188. Как работают Spring AOP proxies и self-invocation?** · middle
**Ориентир:** Многие возможности Spring реализованы proxy-объектом, который перехватывает внешний вызов bean. Вызов метода через `this` обходит proxy, поэтому аннотация вроде `@Transactional` на вызываемом методе может не сработать.

<a id="java-189"></a>

**189. Что включает Spring Boot auto-configuration?** · junior/middle
**Ориентир:** Boot условно регистрирует конфигурацию по classpath, существующим beans, properties и другим условиям. Пользовательский bean или настройка часто заменяет default; отчёт conditions помогает понять принятое решение.

<a id="java-190"></a>

**190. Чем starter отличается от auto-configuration?** · junior/middle
**Ориентир:** Starter — удобный набор зависимостей, а auto-configuration — код, создающий beans при выполнении условий. Они часто поставляются вместе, но решают разные задачи.

<a id="java-191"></a>

**191. Как устроены externalized configuration и profiles в Spring Boot?** · middle
**Ориентир:** Значения приходят из properties/YAML, environment variables, command line и других property sources с определённым приоритетом. Profiles включают группы настроек, но секреты лучше получать из secret storage, а не хранить в профильном файле репозитория.

<a id="java-192"></a>

**192. Почему `@ConfigurationProperties` предпочтительнее множества `@Value`?** · middle
**Ориентир:** Она типобезопасно связывает группу настроек, поддерживает validation и метаданные IDE. Один класс также делает контракт конфигурации заметным и тестируемым.

<a id="java-193"></a>

**193. Как различаются filter, interceptor и controller advice в Spring MVC?** · middle
**Ориентир:** Servlet filter работает до DispatcherServlet и подходит для низкоуровневого HTTP-контекста, interceptor окружает обработчик MVC, а advice централизует работу контроллеров, например mapping исключений. Выбор зависит от слоя, где доступен нужный контекст.

<a id="java-194"></a>

**194. Как Spring MVC преобразует HTTP-запрос в аргументы controller?** · junior/middle
**Ориентир:** Handler mapping выбирает метод, argument resolvers извлекают path/query/header/body, а message converters сериализуют тело. Валидация запускается по `@Valid`/`@Validated`, если настроены constraints.

<a id="java-195"></a>

**195. Как проектировать единый формат ошибок REST в Spring?** · middle
**Ориентир:** `@ControllerAdvice` сопоставляет ожидаемые исключения со статусом и стабильным DTO ошибки, например Problem Details. В ответе полезны машинный код, понятное сообщение и correlation ID, но не stack trace и внутренние SQL-детали.

<a id="java-196"></a>

**196. Что делает `@Transactional`?** · junior/middle
**Ориентир:** Обычно proxy открывает или присоединяет транзакцию перед методом и завершает её после возврата или ошибки. Аннотация не превращает удалённые вызовы в одну ACID-транзакцию и зависит от выбранного transaction manager.

<a id="java-197"></a>

**197. Когда Spring откатывает транзакцию по умолчанию?** · middle
**Ориентир:** В типичной декларативной конфигурации rollback выполняется для `RuntimeException` и `Error`, но не для checked exceptions без явного правила. Пойманное внутри метода исключение или self-invocation может изменить ожидаемое поведение.

<a id="java-198"></a>

**198. Чем propagation `REQUIRED` отличается от `REQUIRES_NEW`?** · middle/senior
**Ориентир:** `REQUIRED` присоединяется к текущей транзакции или создаёт новую, `REQUIRES_NEW` приостанавливает текущую и открывает независимую. Второй режим расходует отдельное соединение и может создавать неожиданные блокировки или частичный commit.

<a id="java-199"></a>

**199. Что означают уровни изоляции транзакций?** · middle
**Ориентир:** Они задают допустимые аномалии конкурентного чтения, но точные гарантии зависят от СУБД и MVCC. Уровень выбирают по инвариантам и проверяют конкурентным тестом, а не только по названию enum.

<a id="java-200"></a>

**200. Как Spring Data создаёт реализации repository?** · junior/middle
**Ориентир:** Spring регистрирует proxy для repository-интерфейса, строит запрос из имени метода или использует явно заданный query. Длинные derived query names лучше заменить понятным запросом, specification или отдельной реализацией.

<a id="java-201"></a>

**201. Чем pagination через offset отличается от keyset pagination?** · middle/senior
**Ориентир:** Offset прост и позволяет перейти к номеру страницы, но на больших смещениях дорог и нестабилен при изменениях данных. Keyset продолжает после последнего сортировочного ключа и требует уникального стабильного порядка.

<a id="java-202"></a>

**202. Как устроена filter chain в Spring Security?** · middle
**Ориентир:** Набор servlet filters извлекает credentials, выполняет authentication, сохраняет security context и применяет authorization. Порядок фильтров важен, а пользовательский фильтр нужно ставить относительно известного стандартного фильтра.

<a id="java-203"></a>

**203. Чем authentication отличается от authorization?** · junior
**Ориентир:** Authentication устанавливает, кто выполняет запрос, authorization решает, разрешено ли ему конкретное действие над ресурсом. Проверки доступа нужны и на URL, и при необходимости на method/domain level.

<a id="java-204"></a>

**204. Чем session-based authentication отличается от JWT bearer tokens?** · middle
**Ориентир:** Сессия хранит server-side состояние и легко отзывается, bearer JWT обычно проверяется локально и сложнее немедленно отозвать. JWT следует валидировать по подписи, issuer, audience и времени, а срок жизни и rotation выбирать по модели угроз.

<a id="java-205"></a>

**205. Когда важна CSRF-защита?** · middle
**Ориентир:** CSRF актуальна, когда браузер автоматически прикладывает credentials, например cookie, к изменяющему запросу. Отключать защиту допустимо после анализа схемы аутентификации; CORS сам по себе CSRF не предотвращает.

## SQL, JDBC, JPA и Hibernate { #persistence }

<a id="java-206"></a>

**206. Как безопасно выполнять параметризованный SQL через JDBC?** · junior
**Ориентир:** Использовать `PreparedStatement` и bind-параметры вместо конкатенации пользовательских значений. Имена таблиц и сортировки параметрами не связываются, поэтому их выбирают из allowlist.

<a id="java-207"></a>

**207. Зачем приложению connection pool?** · junior/middle
**Ориентир:** Создание подключения дорого, поэтому pool переиспользует ограниченное число соединений. Размер согласуют с лимитом БД, временем запросов и количеством экземпляров; слишком большой pool усиливает перегрузку.

<a id="java-208"></a>

**208. Как правильно закрывать JDBC resources?** · junior
**Ориентир:** `Connection`, `Statement` и `ResultSet` закрывают через try-with-resources, обычно в обратном порядке. При pool закрытие connection возвращает его в pool, а не обязательно закрывает физическое соединение.

<a id="java-209"></a>

**209. Какие свойства SQL-индекса важны разработчику?** · middle
**Ориентир:** Индекс ускоряет подходящие чтения ценой места и стоимости записи; порядок колонок в составном индексе влияет на применимость. Решение подтверждают планом выполнения и production-подобными объёмами данных.

<a id="java-210"></a>

**210. Что такое persistence context в JPA?** · middle
**Ориентир:** Это unit of work, который отслеживает managed entities и гарантирует identity для одной сущности по ключу внутри контекста. При flush накопленные изменения синхронизируются с БД, но commit может произойти позже.

<a id="java-211"></a>

**211. Какие состояния entity различает JPA?** · junior/middle
**Ориентир:** Новая entity transient, присоединённая к persistence context — managed, удалённая помечена removed, отсоединённая — detached. Dirty checking автоматически сохраняет изменения managed entity при flush.

<a id="java-212"></a>

**212. Чем `persist` отличается от `merge`?** · middle
**Ориентир:** `persist` делает переданный новый объект managed, а `merge` копирует состояние переданного объекта в managed экземпляр и возвращает его. Исходный detached-объект после `merge` managed не становится.

<a id="java-213"></a>

**213. Что такое lazy loading и `LazyInitializationException`?** · junior/middle
**Ориентир:** Lazy association загружается при обращении, часто через proxy или обёртку коллекции. После закрытия persistence context догрузить данные нельзя, поэтому границы выборки проектируют в query/service, а не держат сессию открытой случайно.

<a id="java-214"></a>

**214. Что такое проблема N+1 запросов?** · middle
**Ориентир:** После одного запроса списка приложение выполняет отдельный запрос для связи каждой строки. Её находят по SQL-метрикам и исправляют подходящим fetch join, entity graph, batch fetching или специализированной проекцией, учитывая размер результата.

<a id="java-215"></a>

**215. Чем fetch join отличается от обычного `join` в JPQL?** · middle
**Ориентир:** Обычный join участвует в фильтрации или выборе, но не обязан инициализировать association. Fetch join указывает загрузить связь в том же запросе; fetch нескольких коллекций и pagination требуют осторожности.

<a id="java-216"></a>

**216. Как работают optimistic и pessimistic locking?** · middle/senior
**Ориентир:** Optimistic locking сравнивает версию и обнаруживает конфликт при записи, pessimistic просит БД удерживать lock. Первый хорош при редких конфликтах с retry, второй может быть нужен при высокой конкуренции, но увеличивает ожидания и риск deadlock.

<a id="java-217"></a>

**217. Почему `equals` и `hashCode` у JPA entity сложны?** · senior
**Ориентир:** Сгенерированный id может отсутствовать до persist, proxy меняет фактический класс, а изменяемые поля ломают hash-коллекции. Стратегию выбирают по стабильному business key или аккуратному контракту id и проверяют на transient/managed/detached объектах.

<a id="java-218"></a>

**218. Для чего нужны Flyway или Liquibase?** · junior/middle
**Ориентир:** Они версионируют и последовательно применяют изменения схемы БД. Применённые миграции обычно не переписывают; сложные изменения делают совместимыми с поэтапным rollout приложения.

<a id="java-219"></a>

**219. Как безопасно изменить обязательную колонку без остановки сервиса?** · senior
**Ориентир:** Применяют expand-and-contract: добавить nullable/совместимую структуру, развернуть код с dual read/write или backfill, заполнить данные и только затем ужесточить constraint и удалить старое. Каждый этап должен работать при одновременном существовании соседних версий приложения.

## REST, messaging и Kafka { #integration }

<a id="java-220"></a>

**220. Какие свойства HTTP-методов учитывают в REST API?** · junior
**Ориентир:** Важны safety и idempotency: GET не должен менять состояние, PUT и DELETE должны быть идемпотентны по смыслу, POST обычно нет. Реализация обязана учитывать повторы запросов из-за сетевых сбоев.

<a id="java-221"></a>

**221. Как выбрать HTTP status code для ошибки?** · junior/middle
**Ориентир:** Код отражает класс результата: ошибка входа клиента, отсутствие authentication, запрет, отсутствие ресурса, конфликт состояния или сбой сервера. Бизнес-ошибку не следует маскировать ответом `200 OK` только ради единого envelope.

<a id="java-222"></a>

**222. Как версионировать REST API?** · middle
**Ориентир:** Сначала стремятся к обратно совместимым изменениям: добавлять необязательные поля и не менять смысл существующих. Breaking changes требуют явной версии, периода миграции, метрик использования и плана отключения старого контракта.

<a id="java-223"></a>

**223. Что такое идемпотентность команды и как её обеспечить?** · middle/senior
**Ориентир:** Повтор одной логической команды не должен создавать дополнительный эффект. Обычно используют idempotency key, уникальное ограничение и атомарное сохранение результата, а не только проверку «есть ли запись» перед insert.

<a id="java-224"></a>

**224. Чем очередь сообщений отличается от publish/subscribe?** · junior/middle
**Ориентир:** В очереди сообщение обычно обрабатывает один competing consumer, а pub/sub доставляет событие нескольким независимым подписчикам. Конкретные гарантии определяет брокер, модель consumer groups и срок хранения.

<a id="java-225"></a>

**225. Что означают at-most-once, at-least-once и exactly-once?** · middle
**Ориентир:** At-most-once допускает потерю без дублей, at-least-once — повторы без потери после подтверждения, exactly-once требует строго определить границу эффекта. Даже при broker-level exactly-once внешняя БД или HTTP-вызов требуют собственной идемпотентности.

<a id="java-226"></a>

**226. Как Kafka распределяет сообщения по partitions?** · junior/middle
**Ориентир:** Producer выбирает partition, часто по hash ключа; порядок гарантируется только внутри одной partition. Число partitions ограничивает параллелизм consumer group и влияет на масштабирование и распределение ключей.

<a id="java-227"></a>

**227. Как работает Kafka consumer group и rebalance?** · middle
**Ориентир:** Каждая partition назначается максимум одному consumer внутри группы, а разные группы читают независимо. При изменении состава или metadata происходит rebalance; долгий handler и неверные timeouts могут вызвать повторную обработку.

<a id="java-228"></a>

**228. Когда подтверждать Kafka offset?** · middle/senior
**Ориентир:** Commit до эффекта рискует потерять сообщение, после эффекта — допускает повтор при сбое между эффектом и commit. Поэтому обработчик проектируют идемпотентным либо атомарно связывают данные и позицию в поддерживаемой транзакционной модели.

<a id="java-229"></a>

**229. Что такое transactional outbox?** · senior
**Ориентир:** Бизнес-изменение и запись будущего сообщения сохраняются в одной локальной транзакции БД, после чего relay публикует outbox в брокер. Возможны повторные публикации, поэтому потребители всё равно должны учитывать дубликаты.

## Архитектура, resilience, безопасность и observability { #architecture }

<a id="java-230"></a>

**230. Когда модульный монолит предпочтительнее микросервисов?** · middle/senior
**Ориентир:** Когда доменные границы ещё меняются, команда небольшая, а независимое масштабирование и deployment не окупают распределённую сложность. Хорошие внутренние модули сохраняют возможность выделить сервис позже на основе измеренной потребности.

<a id="java-231"></a>

**231. Как определить границу микросервиса?** · senior
**Ориентир:** Граница следует business capability, ownership данных и необходимости независимого изменения, а не таблице или техническому слою. Чрезмерно связанные синхронные вызовы и общая БД обычно указывают на неверное разделение.

<a id="java-232"></a>

**232. Почему распределённая транзакция часто заменяется saga?** · senior
**Ориентир:** Saga связывает локальные транзакции событиями или оркестрацией и применяет компенсирующие действия при сбое. Она принимает eventual consistency и требует явных состояний, идемпотентности и обработки необратимых действий.

<a id="java-233"></a>

**233. Как выбирать timeout для внешнего вызова?** · middle/senior
**Ориентир:** Timeout должен укладываться в end-to-end deadline и опираться на latency distribution зависимости, а не на произвольное круглое число. Нужны отдельные connect/read limits и распространение оставшегося deadline вниз по цепочке.

<a id="java-234"></a>

**234. Когда retry помогает, а когда усугубляет сбой?** · middle/senior
**Ориентир:** Retry полезен для временной ошибки идемпотентной операции с ограниченным числом попыток, backoff и jitter. Повтор permanent error или перегруженного downstream умножает нагрузку и задержку.

<a id="java-235"></a>

**235. Для чего нужен circuit breaker?** · middle
**Ориентир:** Он временно прекращает вызовы явно нездоровой зависимости и периодически проверяет восстановление, уменьшая расход ресурсов и каскадный отказ. Порог, окно и fallback должны соответствовать SLO; breaker не лечит сам сервис.

<a id="java-236"></a>

**236. Что такое bulkhead и backpressure?** · senior
**Ориентир:** Bulkhead ограничивает ресурсы для отдельной зависимости или класса запросов, чтобы сбой не исчерпал всё. Backpressure замедляет или отвергает входную нагрузку, когда потребитель не успевает; неограниченная очередь лишь скрывает перегрузку.

<a id="java-237"></a>

**237. Как хранить и передавать секреты приложения?** · middle
**Ориентир:** Секреты получают во время запуска из управляемого secret store или защищённого окружения с минимальными правами и rotation. Их нельзя коммитить, логировать или включать в diagnostics; утёкший секрет нужно отозвать, а не просто удалить из последнего commit.

<a id="java-238"></a>

**238. Какие меры защищают Java REST API кроме authentication?** · middle/senior
**Ориентир:** Нужны object-level authorization, validation, лимиты размера и частоты, безопасная десериализация, TLS, управление секретами и audit критичных действий. Политика ошибок не должна раскрывать stack traces, credentials или наличие чужих ресурсов.

<a id="java-239"></a>

**239. Чем logs, metrics и traces дополняют друг друга?** · junior/middle
**Ориентир:** Metrics показывают агрегированный тренд и запускают alerts, traces связывают путь запроса между компонентами, logs дают подробные события. Correlation/context fields позволяют переходить между сигналами, а high-cardinality данные требуют контроля стоимости.

<a id="java-240"></a>

**240. Что такое SLI, SLO и error budget?** · senior
**Ориентир:** SLI — измеряемый показатель пользовательской надёжности, SLO — целевое значение за окно, error budget — допустимое отклонение от цели. Эти понятия помогают принимать решения о релизах и надёжности, если измерение отражает реальный пользовательский результат.
