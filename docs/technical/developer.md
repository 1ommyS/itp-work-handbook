# Техническая подготовка разработчика

Начните с требований вакансий и формата секций. Отметьте повторяющиеся темы и оцените себя: **объясняю → применяю → диагностирую → выбираю компромисс**.

Глубина зависит от специализации. Если Kafka не связана с ролью, приоритетнее ключевой фреймворк и качество кода.

## Что повторять и как проверять

| Область | Базовый уровень / junior | Middle–senior и практическая проверка |
| --- | --- | --- |
| Язык | Типы, коллекции, функции, ошибки, память и ресурсы | Runtime, профилирование, стоимость абстракций. Объясните поведение короткого кода и перепишите его безопаснее |
| Алгоритмы и структуры | Массив, хеш-таблица, стек, очередь, дерево, сложность | Выбор структуры под ограничения, оценка памяти. Практика по [паттернам](algorithms.md) |
| Базы данных | Ключи, связи, индексы, транзакции | Изоляция, блокировки, план запроса, миграции, репликация. Разберите медленную операцию |
| SQL | JOIN, GROUP BY, NULL, фильтрация, агрегаты | Оконные функции, дедупликация, корректность на дублях, EXPLAIN. Напишите запрос на маленьких данных вручную |
| Сети | DNS, TCP, TLS, HTTP, коды ответов, таймаут | Прокси, пулы соединений, повторы, идемпотентность. Найдите, где может зависнуть запрос |
| Linux | Процессы, права, файлы, переменные окружения, логи | CPU, память, диск, сокеты, сигналы. Составьте план диагностики без опасных команд |
| Git | Ветка, commit, diff, merge, конфликт, revert | Rebase, bisect, стратегия истории. В учебном repo исправьте конфликт и отмените изменение |
| Docker | Образ/контейнер, Dockerfile, volume, порт, переменные | Слои, воспроизводимость, права, healthcheck, ограничения ресурсов. Соберите и запустите приложение по README |
| Kafka / брокеры | Producer, consumer, очередь/лог, подтверждение, повтор | Партиции, consumer group, порядок, offset, lag, дубликаты, dead-letter. Объясните восстановление после сбоя обработчика |
| Concurrency | Поток/процесс/async, race condition, lock | Deadlock, cancellation, bounded queue, backpressure, атомарность. Разберите гонку и гарантии решения |
| System design | Компоненты собственного приложения и модель данных | Требования, нагрузка, отказоустойчивость, стоимость и эксплуатация; [отдельная глава](system-design.md) |
| Фреймворк | Жизненный цикл, конфигурация, обработка запроса, тестирование | Транзакционные границы, расширение, производительность, версии. Разберите поведение используемой версии |
| Code review | Читаемость, корректность, ошибки, базовые тесты | Конкурентность, безопасность, совместимость, эксплуатация. Разделите блокирующее замечание и предпочтение |
| Debugging | Воспроизведение, логи, минимальный пример | Гипотезы, метрики, tracing, профиль, проверка исправления. Покажите последовательность, а не список инструментов |

## Поправка на специализацию

- **Backend:** транзакции, API, сетевые ошибки, брокеры и взаимодействие сервисов; распределённые системы углубляйте по требованиям роли.
- **Frontend:** JavaScript/TypeScript, event loop, браузер, HTTP, доступность, состояние, рендеринг, тесты и производительность. Не заменяйте это Kafka.
- **Mobile:** жизненный цикл, состояние, память, потоки, офлайн-режим, сеть, хранение секретов, публикация и диагностика сбоев.
- **Embedded / системное ПО:** память, указатели, конкурентность, ОС, ограничения устройства, протоколы и диагностика; web-стек может быть не нужен.

Составьте десять вопросов по своему фреймворку: где начинается транзакция, как отменяется запрос, почему компонент перерисовывается. Проверяйте ответы для актуальной версии.

## Одна связная тренировка

Возьмите знакомое приложение и выполните четыре задания:

1. Объясните путь запроса от клиента до базы, включая ошибки и таймауты.
2. Напишите SQL «последний заказ каждого клиента», уточнив, что делать при одинаковом времени и клиентах без заказов.
3. Найдите потенциальный повтор обработки события. Расскажите, как защитить бизнес-операцию от дублей, даже если брокер доставит сообщение повторно.
4. Проведите review небольшого изменения: сначала поведение и данные, затем тесты, затем читаемость. Предложите конкретное исправление.

Junior разбирает локальный сценарий; senior добавляет сбои, конкурентность, наблюдаемость и безопасное изменение. Для «exactly once» уточняйте границу гарантии.

## План диагностики вместо угадывания

Для «сервис стал медленным» уточните масштаб, начало, метрики и последние изменения. Разделите клиент, сеть, приложение и зависимости; проверьте гипотезу, предложите безопасное снижение последствий и проверку исправления.

## Как распределить время

Разделите пробелы на обязательные, частые на ближайшей секции и дополнительные. После интервью обновляйте список по своим затруднениям. Чередуйте чтение с упражнением и объяснением вслух.

Материалы: [PostgreSQL Tutorial](https://www.postgresql.org/docs/current/tutorial.html), [Pro Git](https://git-scm.com/book/ru/v2), [Docker](https://docs.docker.com/get-started/), [Kafka](https://kafka.apache.org/documentation/), [MDN: HTTP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview). Выбирайте документацию нужной версии.

## Что сделать прямо сейчас

- [ ] Выберите пять обязательных тем из своих вакансий.
- [ ] Для каждой подготовьте объяснение и небольшое упражнение.
- [ ] Проведите пробное review чужого учебного pull request.
- [ ] Разберите один реальный баг: симптом, гипотеза, проверка, исправление.
- [ ] Уберите из ближайшего плана темы, не связанные с вашей ролью.
