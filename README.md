# Работа в IT — handbook 2026

Практическое руководство по поиску работы в IT в России: от выбора роли и подготовки резюме до переговоров и проверки оффера. Для разработчиков, QA, аналитиков, DevOps/SRE, дизайнеров, продактов и смежных специалистов — от первого коммерческого опыта до senior и team lead.

Срез источников — **6 сентября 2026 года**. Дата публикации исследования и период его данных указаны отдельно. Рекомендации по планированию поиска и числу откликов не выдаются за статистику рынка. Зарплатные примеры — учебные расчёты, если прямо не указан источник.

## Локальный запуск одной командой

Требуется Python **3.10+** с модулем `venv` (рекомендуется 3.12; CI использует 3.12). Git нужен для клонирования и дат изменения страниц. Для первой установки зависимостей нужен доступ к PyPI; дальнейший запуск с установленными зависимостями не требует интернета.

Из корня репозитория:

```bash
python scripts/docs.py serve
```

Скрипт сам создаст `.venv`, установит закреплённые зависимости и запустит сайт по адресу [http://127.0.0.1:8000/itp-work-handbook/](http://127.0.0.1:8000/itp-work-handbook/). Активация виртуального окружения и ручная настройка не нужны. Изменения Markdown и конфигурации отображаются автоматически. Остановить сервер: `Ctrl+C`.

Если система использует имя `python3`, замените `python` на `python3` во всех командах. В Windows также можно использовать `py`. Если порт занят:

```bash
python scripts/docs.py serve --dev-addr 127.0.0.1:8001
```

## Установка, сборка и проверка

| Команда | Действие |
| --- | --- |
| `python scripts/docs.py bootstrap` | Только подготовить `.venv` и установить зависимости |
| `python scripts/docs.py serve` | Локальный сервер с автоматическим обновлением |
| `python scripts/docs.py build` | Строгая сборка MkDocs в `site/` |
| `python scripts/docs.py check` | Проверить полноту nav, незавершённые страницы, собрать сайт, проверить локальные ссылки и якоря в HTML |

Все команды сами подготавливают зависимости. После изменения `requirements.txt` скрипт переустанавливает их по хешу файла. Ошибки установки и проверки возвращают ненулевой код завершения.

Внешние ссылки не проверяются сборкой: доступность сети и антибот-защита не должны ломать локальный запуск. Актуальность фактов и источников проверяется редактором отдельно.

Если предпочитаете обычный MkDocs, после `bootstrap` доступны `.venv/Scripts/python -m mkdocs serve` в Windows или `.venv/bin/python -m mkdocs serve` в macOS/Linux. Прямой вызов MkDocs оставляет git-даты выключенными; `scripts/docs.py` включает их автоматически, когда у `docs/` есть история коммитов.

## Как устроен проект

```text
docs/
  index.md                 # вход и маршруты чтения
  getting-started/          # рынок, цель, план и старт без опыта
  resume/                  # резюме, примеры, профиль
  job-search/              # площадки, отклики, рекрутер, отказы
  interviews/              # процесс, STAR, вопросы компании
  technical/               # подготовка по ролям и форматам
  salary/                  # переговоры и оффер
  templates/               # формы, сообщения, чек-листы
  resources/               # источники и методология
mkdocs.yml                 # сайт, тема, плагины, Markdown, nav
requirements.in            # прямые зависимости
requirements.txt           # закреплённые прямые и транзитивные зависимости
scripts/docs.py            # единая команда bootstrap / serve / build / check
scripts/check_docs.py      # проверки источников и готового HTML
.github/workflows/docs.yml # CI и публикация по ручному запуску
.vscode/settings.json      # схема YAML и UTF-8
```

Как в `itp-ebook`, используется **MkDocs + Material for MkDocs**: Markdown в `docs/`, явная навигация в `mkdocs.yml`, русскоязычный поиск, светлая и тёмная темы, блоки admonition, сворачиваемые блоки, подсветка кода, чек-листы, git-даты. Локальные шрифты системы не требуют обращения к Google Fonts.

Из референса перенесена инфраструктурная модель. Добавлены воспроизводимые зависимости, единые команды и проверки. Не перенесены главы о Java, личные социальные ссылки, неиспользуемые математические расширения и переключатель версий `mike`: handbook сейчас публикуется одним актуальным изданием. Неактивный дубль `.github/workflow` заменён одним рабочим каталогом `.github/workflows`.

## Добавление страницы и sidebar

1. Создайте Markdown-файл в подходящем разделе `docs/`, например `docs/job-search/networking.md`.
2. Добавьте один заголовок `# Название`. Начните с задачи читателя, затем дайте шаги, пример, ошибки и блок `## Что сделать прямо сейчас` с 3–7 действиями.
3. Добавьте страницу в `nav` файла `mkdocs.yml` в нужном порядке:

   ```yaml
   - Поиск вакансий:
       - Каналы поиска: job-search/channels.md
       - Networking: job-search/networking.md
   ```

4. Для ссылок на другие главы используйте относительные пути к `.md`, например `[Резюме](../resume/resume.md)`. Для якорей используйте фактический идентификатор заголовка из локального сайта. Ссылки на файлы вне `docs/` не попадут в сайт.
5. Укажите первичный источник, дату его публикации/данных и ограничения для изменяющихся фактов. Добавьте источник в `docs/resources/sources.md`. Отдельно обозначайте редакционные рекомендации и учебные примеры.
6. Запустите `python scripts/docs.py check`, откройте страницу локально и проверьте таблицы, чек-листы и читательский маршрут.

Верхние вкладки и левый sidebar формируются из `nav`; порядок страниц также определяет кнопки «Назад»/«Далее». Правое оглавление формируется автоматически из заголовков текущей страницы. Проверка требует, чтобы каждая Markdown-страница была в nav ровно один раз.

Git-даты показывают изменения файла, а не дату проверки фактов. В пустом репозитории, архиве без `.git` или при недоступной истории они отключаются автоматически; заявленная дата исследования остаётся в тексте. Для принудительного отключения передайте `ENABLE_GIT_DATES=false` через переменную окружения.

## CI и публикация

GitHub Actions выполняет `check` на push в `main` и pull request, затем сохраняет готовый сайт как артефакт `handbook-site`. История Git загружается полностью для корректных дат.

Публикация повторяет механизм референса — `mkdocs gh-deploy` в ветку `gh-pages`. Чтобы опубликовать сайт, в GitHub запустите workflow **Documentation** через **Run workflow** на ветке `main` с флагом `deploy`. Публикация выполняется только после успешной проверки. В **Settings → Pages** укажите **Deploy from a branch → gh-pages → /(root)**. Ожидаемый адрес задан в `site_url`; наличие конфига не означает, что сайт уже опубликован.

Если репозиторий переименован или перенесён, обновите `site_url`, `repo_name`, `repo_url` и `edit_uri` в `mkdocs.yml`.

## Обновление зависимостей

`requirements.in` фиксирует прямые зависимости; `requirements.txt` — полный набор версий, проверенный сборкой. Меняйте версии осознанно, устанавливайте их в чистое временное окружение, обновляйте lock и запускайте `check`. Не генерируйте lock из глобального Python с посторонними пакетами. После обновления проверяйте Python 3.12 в CI и используемую локальную версию Python.

При редакционных правках проверяйте, что соседние главы не противоречат друг другу, примеры не выдают вымышленные достижения за реальные, а изменившиеся российские правила и возможности площадок подтверждены актуальными источниками.
